# 清晰具体的指令

  1. 角色定义
    1. 你是一名python开发程序员
  2. 使用分隔符清晰地表示输入的不同部分：
    1. 使用诸如 ```、"""、< >、 等符号将指令与待处理文本分开
  3. 寻求结构化的输出：
    1. 要求模型以 JSON 或 HTML 格式生成内容。
  4. 清晰的边界：明确告诉agent 不能做什么
    1. 如：“如果工具返回错误，请尝试修复参数重试一次，若依然失败则报错，不要虚构结果。”
  5. 检查是否满足条件：告诉模型，如果输入不符合某种特定要求，该如何反馈，而不是胡编乱造
    1. 示例：如果文本中包含一系列指令，请将其重写为步骤格式。如果不包含指令，请直接回复“未提供步骤”
  6. 少样本提示：在让模型干活前，先给它一两个成功的“打样”例子
    1. 示例：
      • 用户：告诉我什么是耐心。 助手：耐心是长流的细水，是等待花开的沉静。 用户：告诉我什么是勇气。 助手：[模型会模仿上述风格回复]

# 推理模式优化

  1. ReAct 框架 (Reasoning + Acting)：强制模型按照 Thought（思考）-> Action（行动）-> Observation（观察） 的循环运行
  2. Plan-and-Execute (先计划后执行)：对于长任务，在 Prompt 中要求 Agent 先生成一份完整的步骤清单（Plan），再逐一执行。这能有效防止 Agent 在中途“迷路”
  3. 思维链 (Chain of Thought, CoT)：在指令中加入“请一步步思考（Let's think step by step）”，能显著提高逻辑推理类任务的成功率

# 工具描述优化

  1. 极其具体的参数描述：不要只写 city，要写 city: 城市的名称，例如 "Beijing" 或 "New York"。
  2. 使用场景指导：在工具描述中加入“当用户询问天气或穿着建议时，请调用此工具”。
  3. 少样本示例 (Few-shot)：提供 1-2 个“问题 -> 思考 -> 调用工具 -> 结果”的例子。模型模仿例子的能力远强于理解枯燥的指令

# 动态上下文与反馈优化

  1. 反思与自我修正 (Self-Reflection)：在 Prompt 中加入一段逻辑：“在给出最终答案前，请检查你的回答是否完全解决了用户的问题，以及是否存在逻辑矛盾。”
  2. 错误处理机制：预设当工具返回空值或报错时的应对策略。
    • 提示词示例：“如果搜索结果为空，请尝试更换关键词再次搜索，不要直接回复不知道。”
  3. 动态少样本 (Dynamic Few-shot)：根据用户的问题，从向量数据库中检索最相关的几个成功案例放入 Prompt 中（这需要配合 RAG 技术）。

# 核心原则二：给模型“思考”的时间

核心思想：如果任务太复杂，模型会像人一样因匆忙而犯错。你需要引导它进行逻辑推理。

  1. 指定完成任务所需的步骤

    • 技巧：将复杂的任务拆解为具体的序列步骤。

    • 示例：

      • 第一步：用一句话总结以下文本。
        • 第二步：将总结翻译成英文。
        • 第三步：列出英文总结中的人名。
        • 第四步：输出一个 JSON 对象。

  2. 指导模型在下结论前找出一个自己的解决方案

    • 技巧：不要直接问模型“这个答案对不对”，而是让它先自己算一遍，再对比。

    • 场景：比如让模型批改数学题，直接问对错它可能会被错误的解题步骤误导。

    • 示例：

      • 请先自己计算这道题的答案，然后将你的答案与学生的答案进行比较，判断学生的解答是否正确。

# 迭代与优化（写 Agent 的常态）

  • 没有完美的 Prompt：写 Agent 并不是一次写对就万事大吉了。
  • 流程化建议：
    • 初试：写一个简单清晰的 Prompt。
    • 分析：查看输出，发现哪里不满意（比如：太长了、格式不对、逻辑乱了）。
    • 改进：针对性地添加限制或示例。
    • 循环：重复上述过程直到稳定。

# RAG

# 什么叫RAG？

  1. RAG = 检索增强生成（Retrieval-Augmented Generation）

# 作用是什么？

  1. 解决大模型不知道新知识、幻觉的问题
  2. 不用重新训练模型，成本低、安全可控

# 常见分类及对应的流程是什么？

# 基础 RAG

  1. 最简单：切分→向量→检索→生成。适合简单问答。

# 高级 RAG（优化版）

  1. 召回前：查询优化、重写
  2. 召回中：多路召回、混合检索（关键词+向量）
  3. 召回后：重排序（Rerank），上下文压缩

# 召回前：

  1. 多查询重写
    1. 原理：对原始查询，使用LLM生成N个语义相似但表述不同的查询变体
    2. 作用：覆盖同一意图的不同表达方式，避免因措辞差异导致的漏检。
    3. 实现：提示词设计为“请为以下问题生成5个语义相同但措辞不同的变体”。
    4. 后续处理：并行检索所有变体，合并去重后送入LLM生成。
  2. 子查询分解
    • 原理：将复杂、多跳的查询拆解为多个独立、简单的子查询。
    • 场景：适用于需要对比、因果推理或多步骤推理的问题。例如，“比较A公司和B公司2023年的营收” → 拆解为“A公司2023年营收”和“B公司2023年营收”。
    • 实现：通过思维链提示或预定义规则进行分解。可串行检索（依赖前一个检索结果进行下一步）或并行检索后合并。
  3. 上下文嵌入：
    • 原理：将对话历史、用户画像或前序检索结果作为上下文，与当前查询拼接，形成完整的查询语句。
    • 场景：多轮对话中消除指代（“它”、“那个方案”）和省略。

# 召回中

概念 一句话解释
多路召回 从多个数据源或通路分别检索，合并结果，提升召回覆盖面
混合检索 融合向量+关键词等多种检索技术，兼顾语义理解与精确匹配 向量检索:理解语义、处理同义词、泛化能力强
关键词检索:精确匹配、可解释性强、速度快
关系 混合检索是多路召回的核心组成部分，两者通常配合使用

# 召回后

概念 一句话解释 核心价值
重排序 用更精准的模型对初检结果重新打分排序 提升排序精度，确保最相关文档进入LLM
上下文压缩 对文档进行提取/摘要/剪枝，去除冗余 减少噪音、节省token、提升生成质量

# 模块化 RAG

  1. 可插拔：不同场景用不同检索策略。

# 面试高频三连问（标准答案）

  1. RAG 和 Fine-tuning 区别？

    1. RAG：外挂知识库，不改模型，安全、实时、成本低。
    2. 微调：改模型权重，适合固定风格/专业领域，成本高。

  2. Agent 和普通 LLM 区别？

    1. LLM：你问啥它答啥，被动。
    2. Agent：有目标、会思考、会用工具、自主完成任务。

  3. Agent 和工作流区别？

    1. 工作流：固定步骤，按流程跑。
    2. Agent：动态思考，自主决策下一步。

# 在RAG过程中，数据是如何获取和构造的（清洗去重过滤）

# 获取：

  1. 非结构化数据：PDF 手册、Word 文档、Markdown 笔记。
  2. 半结构化数据：HTML 网页、JSON 日志、邮件记录。
  3. 结构化数据：数据库表（SQL）、Excel 报表（通常需要转换为 Text-to-SQL 或特定的描述性文本）。

# 清洗

  1. 格式剥离：利用 Unstructured 或 PyMuPDF 解析文档，去除页眉、页脚、广告弹窗、非法字符（如 \x0c）。
  2. 噪声过滤：删除过短的句子（如“查看更多”、“点赞”）、乱码文本。
  3. 语义增强：对于图片、表格，利用多模态模型（如 GPT-4o-mini）生成文本描述（Captioning），将其转化为可检索的文本。

# 切片

详见切片详情

# 去重与过滤

  1. 语义去重 (Semantic De-dup)：

    • 计算所有 Chunk 的向量，通过 Cosine Similarity 识别相似度 > 0.95 的块。

    • 策略：只保留最完整的一个，或者合并差异点。

  2. 关键词过滤：

    1. 基于业务黑名单（如敏感词、过时版本号）过滤掉不应被检索的内容。

# RAG的文档切分

# 基于规则的切分

# 一、固定长度切分

  • 按字符数切分：如512、1024字符，可设置重叠区域
  • 按Token数切分：以模型Token数为单位，更符合LLM处理边界
  • 优点：简单、可控、速度快
  • 缺点：可能切断语义完整性

# 二、基于分隔符切分

  • 按段落（\n\n）、句子（.!?）、章节标题切分
  • 保留自然语义边界
  • 优点：语义完整性较好
  • 缺点：长度不固定，可能过长或过短

# 基于文档结构的切分

# 三、Markdown/HTML结构切分

  • 按标题层级（H1、H2、H3）切分
  • 保留列表、表格、代码块完整性
  • 适用于技术文档、网页内容

# 四、PDF/Word文档结构切分

  • 按页、章节、段落识别
  • 结合布局分析（如Unstructured.io (opens new window)）
  • 保留表格、图片等非文本元素

# 语义智能切分

# 五、基于嵌入相似度切分

  • 计算相邻句子的向量相似度
  • 在相似度低的位置切分（语义转折点）
  • 如LlamaIndex的SemanticSplitterNodeParser

# 六、基于模型判别的切分

  • 使用小模型预测切分点
  • 如训练分类器判断句子是否为边界
  • 更智能但成本较高

# 高级切分策略

# 七、滑动窗口与重叠

  • 相邻块设置重叠区域（10%-20%）
  • 避免关键信息被截断在边界

# 八、父子文档切分

  • 大块（父）用于检索，小块（子）用于生成
  • 结合粗粒度召回和细粒度上下文

# 九、元数据关联切分

  • 切分后保留来源信息（文件名、章节、页码）
  • 支持后续过滤和溯源

# 十、多粒度切分

  • 同时生成多种粒度的块
  • 检索时动态选择最合适的粒度

# 五、实践建议

场景 推荐方式 块大小
通用问答 段落切分 + 语义切分 200-500 tokens
技术文档 Markdown结构切分 500-1000 tokens
法律/学术论文 章节+段落切分 300-800 tokens
代码库 函数/类级别切分 按代码结构
长文本 父子文档策略 父:1000-2000,子:200-500

# Agent

# Agent 底层原理（面试官最爱深挖）

一句话：Agent = LLM 做大脑 + 规划 + 工具调用 + 记忆 + 反思

核心 5 组件（背这个）

  1. 大脑（LLM） 负责思考、决策、理解任务。

  2. 记忆（Memory）

    1. 短期记忆：上下文
    2. 长期记忆：向量库/数据库

  3. 工具（Tools） 搜索、代码解释器、API、函数调用（FC）。

  4. 规划（Planning） 拆解任务、多步推理、自主决定怎么做。

  5. 反思（Reflection） 检查结果对不对，错了就修正。

# 标准执行流程（面试直接说）

  1. 理解用户目标

  2. 思考：我要做什么？需要哪些工具？

  3. 调用工具获取信息

  4. 继续推理，直到完成目标

  5. 输出最终结果

# 多 Agent 是什么？协调工作有哪些架构?(如何协调工作？)

  1. 多 Agent = 多个智能体分工协作完成复杂任务。

  2. 特点

    1. 每个 Agent 有专属角色
    2. 互相通信、分工、协作
    3. 能处理复杂、多步骤、跨领域任务

  3. 常见架构

    1. 集中式 有一个“主管 Agent”分配任务。
    2. 分布式 无中心，Agent 之间互相沟通。
    3. 分层式 上层决策，下层执行。

  4. 协调的核心机制：

    1. 状态共享（Shared State）：
      1. 所有 Agent 在同一个“看板”或状态图上共享信息。它记录了当前任务的进度、已获取的中间结果、各 Agent 的私有变量以及对话历史。
      2. 实现方式：
        • 结构化定义：通常使用 TypedDict (Python) 或 JSON Schema 来定义状态结构。
        • Reducer 机制：当 Agent 处理完任务后，它不直接覆盖整个状态，而是通过 Annotated 标记的增量更新函数（如 operator.add）将新信息合并到全局状态中。
    2. 路由机制（Routing）：
      1. 基于条件的路由，决定下一个节点该交给哪个 Agent 处理。类似于程序中的 if-else 或 switch 逻辑，但其判断依据通常是大模型的推理结果。
      2. 实现方式：
        • 静态路由：基于硬编码逻辑（如：若 Agent 返回特定字符则跳转）。
        • 动态路由（LLM Router）：由一个中心化的 Supervisor Agent 分析当前 State，输出下一个执行节点的名称。
        • 条件边缘 (Conditional Edges)：在图结构中定义逻辑分支。
    3. 终止条件（Stopping Criteria）：
      1. 定义任务何时算完成，防止 Agent 陷入死循环（例如两个 Agent 互相踢皮球）。
      2. 实现方式：
        • 目标达成判断：由 LLM 检查当前状态是否满足用户初始需求（如回复中包含 "FINAL ANSWER"）。
        • 最大迭代次数 (Max Loops)：设置硬性上限（如最多流转 10 次），防止 Token 浪费和程序挂死。
        • 特定谓语/标记：Agent 输出特定的停止信号（如调用 __end__ 节点）

  5. 典型应用

    1. 代码开发团队（产品、前端、后端、测试）
    2. 内容创作团队
    3. 企业自动化流程

# 为什么要做agent

之所以要做 Agent 项目，而不是停留在简单的 ChatBot 或 RAG 阶段，主要基于以下三个维度的技术必然性和商业价值：

  1. 从“生成内容”到“解决问题”的跨越
    1. 传统 LLM 主要是文本生成器，它能告诉你“怎么做”，但不能“替你做”。
    2. Agent 的价值：Agent 具备**工具使用（Tool Use）**能力。它能直接调用 API、操作数据库或执行脚本。
  2. 处理复杂长路径任务：
    1. 当一个任务需要多个步骤、多次决策且中间结果会影响后续选择时，单次 Prompt 无法胜任
    2. Agent 的价值：通过规划（Planning）**和**递归式思考（ReAct），Agent 可以将大目标拆解为小步骤。
  3. 连接私有数据与异构系统
    1. 企业内部的数据往往分散在 ERP、CRM、代码库或本地文档中
    2. Agent 的价值：Agent 可以作为中间层，理解自然语言意图后，实时查询异构系统并进行数据加工。

# 记忆的分层管理 (Layered Memory Architecture)

Agent 的记忆通常被划分为三个维度：

  • 感官记忆 (Sensory Memory)：当前的输入（Prompt），处理完即销毁。
  • 短期记忆 (Short-term Memory)：当前会话（Session）的上下文，存储在内存或 Redis 中。
  • 长期记忆 (Long-term Memory)：通过向量数据库（如 Milvus, Pinecone）持久化存储的历史经验和知识。

# 上下文压缩的四种核心策略

当对话轮数过多导致 Token 溢出时，我们会采用以下技术进行“瘦身”：

# A. 滑动窗口法 (Sliding Window)

只保留最近的 $N$ 轮对话。

  • 优点：实现简单，保证了近期的语境最清晰。
  • 缺点：会丢失早期定义的任务目标或背景信息。

# B. 总结压缩法 (Summarization)

利用一个较小的模型（或当前模型）对历史对话进行摘要。

  • 实现：当 Token 达到阈值（如窗口的 80%）时，触发 Summarize_Node，将前 20 轮对话压缩成一段简短的文字，替换掉原始记录。
  • 增量总结：每次只总结新产生的对话，并更新维护一个“全局摘要”。

# C. 语义检索过滤 (Selective Context/RAG)

不按时间顺序加载记忆，而是按相关性加载。

  • 实现：将历史对话切片并向量化。每次提问时，通过相似度检索（Cosine Similarity）只提取与当前问题最相关的 3-5 条历史片段放入上下文。

# D. 关键实体提取 (Entity Extraction)

仅保留对话中的核心要素。例如：用户的偏好、提到的变量名、决策结果。

  • 实现：维护一个结构化的 JSON 对象，专门记录“用户画像”或“任务状态”。

# 记忆管理的最终结果与挑战

  • 结果：Agent 能够在长达数周的交互中依然记住用户的核心需求，同时保持极低的 API 调用成本。
  • Badcase 及其解决：
    • 信息丢失：摘要可能会漏掉关键细节。解决方法：使用递归总结（Recursive Summary），保留一个多级索引，或者结合向量检索。
    • 语义漂移：多次总结后，语义可能走样。解决方法：保留一份原始数据的冷存储（Cold Storage），必要时重新索引。

# agent对于用户意图识别不准确，在工程上有哪些方法进行优化

# 1. 语义 Schema 约束与 Few-shot 引导

大模型在面对模糊指令时容易发散。通过提供结构化的范例，可以极大地收敛其意图判别。

  • 实现方法：在 System Prompt 中定义明确的 Intent Enum（意图枚举），并为每个意图提供 3-5 个典型的 Positive Examples（正例）。
  • 技巧：使用 xml 或 json 格式要求模型输出，例如 <intent>QUERY_MES_LOG</intent>，这比纯文本更易于解析和验证。

# 2. 引入独立的分层路由 (Hierarchical Routing)

不要试图让一个模型同时理解“闲聊”和“复杂的工业指令”。

  • 实现方法：先部署一个轻量级、高响应速度的模型（如 GPT-4o-mini 或本地的 Qwen-7B）作为前置分类器（Classifier）。
  • 逻辑：第一层只分大类（如：技术咨询、设备操作、闲聊）。进入特定大类后，再由专业领域的 Agent 或 Prompt 进一步细化。

# 3. 基于语义向量的检索增强 (Semantic Intent Retrieval)

当意图种类非常多（如超过 50 种）时，Prompt 会因为太长而失效。

  • 实现方法：
    1. 将所有标准意图及对应的示例向量化，存入向量数据库。
    2. 用户输入后，先通过 Vector Search 检索出最相似的 3 个意图示例。
    3. 将这 3 个示例动态注入 Prompt。这被称为 Dynamic Few-shot。

# 4. 引入“澄清机制” (Clarification Loop)

意图识别不准有时是因为用户表达本身具有二义性。

  • 实现方法：设置置信度阈值（Confidence Threshold）。
    • 如果 LLM 输出的意图置信度 < 0.8，Agent 不直接执行，而是反问用户：“您是指‘查询 A1 车间的产量’还是‘修改 A1 车间的排产计划’？”
  • 价值：在工业控制场景下，这种“二次确认”是防止误操作的关键。

# 5. 多维度特征融合 (Feature Fusion)

除了文本内容，结合上下文状态能显著提升准确率。

  • 实现方法：将当前的“环境状态”（如：当前页面 ID、用户角色权限、前三轮对话内容）作为辅助特征输入。
  • 示例：如果用户说“重启它”，若上下文显示刚才在聊“AGV 01”，意图识别应自动补全为“重启 AGV 01”。

# SFT阶段有哪些bad case又是怎么解决的？

在 SFT（Supervised Fine-Tuning，监督微调） 阶段，模型的效果高度依赖于指令对（Instruction-Output Pairs）的质量。大家也都知道“垃圾进，垃圾出”（Garbage In, Garbage Out）是 SFT 最大的挑战

# 模型幻觉与知识冲突 (Hallucination)

  • 现象：模型对于不知道的问题开始“一本正经地胡说八道”，或者 SFT 数据里的知识与模型预训练阶段的知识发生冲突。
  • 解决方法：
    • 知识对齐：对 SFT 数据进行事实核查（可以使用强模型如 GPT-4 进行辅助验证）。
    • 引入“拒绝回答”范式：在数据集中加入一定比例的“我不知道”、“根据现有信息无法回答”的案例，训练模型的边界感。
    • RAG 结合：对于时效性强的知识，不强求 SFT 记忆，而是训练模型生成“查询工具”的指令。

# 回复格式坍塌

  • 现象：要求模型输出 JSON 或 Markdown 表格，但模型输出的括号不闭合、字段缺失或包含多余解释
  • 原因：SFT 数据中格式不规范，或者格式样本多样性不足，导致模型没能学死“结构化输出”的约束。
  • 解决方法：
    • Schema 约束强化：在 Input 侧加入严格的 JSON Schema 定义。
    • 损失函数加权：对格式关键 Token（如 {, [, ]）增加 Loss 权重。
    • Few-shot 注入：在 SFT 的 Prompt 示例中，始终保持统一且严谨的格式规范

# 灾难性遗忘 (Catastrophic Forgetting)

  • 现象：模型学会了特定的业务逻辑（如 MES 调度），但失去了通用的对话能力或逻辑推理能力。
  • 原因：SFT 数据过于单一（全是一个领域的任务），导致模型权重偏移过大。
  • 解决方法：
    • 通用数据混入 (Data Mixing)：在业务 SFT 数据中掺入 5%~10% 的通用高质量对话数据（如 Alpaca 或 ShareGPT 数据集）。
    • LoRA 微调：使用参数高效微调（PEFT）技术，仅更新少量旁路参数，保持基座模型大部分权重冻结。

# 训练数据中的“复读机”与模式过拟合 (Pattern Overfitting)

  • 现象：模型每一句话都以相同的口吻开头（如“好的，关于您的问题...”），或者回复极短、无营养。
  • 原因：数据集中存在大量重复的句式模板。
  • 解决方法：
    • 多样性清洗：利用语义向量对 SFT 数据进行聚类，剔除在同一个聚类中心下过于密集的重复模式数据。
    • 长度奖励与惩罚：在构造数据时，确保 Output 的长度分布合理，避免全是短句

# GRPO的奖励函数是如何设计的？最终的结果是什么？

# GRPO 奖励函数的设计逻辑

在传统的 PPO 算法中，我们需要一个额外的模型（Critic）来估算状态价值。而 GRPO 采用“组内相对竞争”的策略：

# A. 组内采样 (Group Sampling)

对于每一个 Prompt（问题 $q$），模型会生成一组回答 ${o_1, o_2, ..., o_G}$。通常组的大小 $G$ 取值在 8 到 64 之间。

# B. 奖励值计算 (Reward Scoring)

每一个回答 $o_i$ 会通过多个奖励模型 (Reward Models) 或规则检查器 (Rule-based Checkers) 得到一个原始分数 $r_i$。在 DeepSeek-R1 的训练中，主要包含两类奖励：

  • 准确性奖励 (Accuracy Reward)：例如对于数学题，答案是否正确；对于代码题，是否通过了单元测试。
  • 格式奖励 (Format Reward)：强制模型将思考过程放入 <think> 标签，将结果放入 <answer> 标签。

# C. 优势函数标准化 (Advantage Calculation)

这是 GRPO 的核心。它不看绝对分数，而是计算该回答在这一组中的相对排名：

$$A_i = \frac{r_i - \text{mean}(r_1, ..., r_G)}{\text{std}(r_1, ..., r_G)}$$

这意味着：如果一组回答都很差，稍微好一点的那个也会得到正向激励；如果都很优秀，表现平平的那个反而会被惩罚。

# 最终的结果是什么？

GRPO 驱动的训练过程产生了一些现象级的技术结果：

  • “顿悟时刻”（Aha! Moment）：由于奖励函数只奖励正确答案和格式，而不限制中间思考过程，模型学会了自主纠错。它会在 <think> 阶段意识到之前的推理有误，并重新推导。
  • 思维链（CoT）的爆发式增长：模型为了拿到最终的准确性奖励，自动学会了通过增加推理长度（即更深层的思考）来提高正确率。
  • 性能对齐：DeepSeek-R1 仅通过大规模 RL（GRPO），在数学（AIME）、编程（Codeforces）等逻辑推理任务上，达到了与 OpenAI o1 相当的水平。
