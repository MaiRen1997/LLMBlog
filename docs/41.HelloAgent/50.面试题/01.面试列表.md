# 提示词工程

## 提示词相关优化

### 清晰具体的指令

1. 角色定义
   1. 你是一名python开发程序员
2. 使用分隔符清晰地表示输入的不同部分：使用诸如 ```、"""、< >、 等符号将指令与待处理文本分开
3. 寻求结构化的输出：要求模型以 JSON 或 HTML 格式生成内容。
4. 清晰的边界：明确告诉agent 不能做什么
   1. 如：“如果工具返回错误，请尝试修复参数重试一次，若依然失败则报错，不要虚构结果。”
5. 检查是否满足条件：告诉模型，如果输入不符合某种特定要求，该如何反馈，而不是胡编乱造
   1. 示例：如果文本中包含一系列指令，请将其重写为步骤格式。如果不包含指令，请直接回复“未提供步骤”
6. 少样本提示：在让模型干活前，先给它一两个成功的“打样”例子
   1. 示例：
      - 用户：告诉我什么是耐心。 助手：耐心是长流的细水，是等待花开的沉静。 用户：告诉我什么是勇气。 助手：[模型会模仿上述风格回复]

### 推理模式优化

1. ReAct 框架 (Reasoning + Acting)：强制模型按照 `Thought（思考）-> Action（行动）-> Observation（观察）` 的循环运行
2. Plan-and-Execute (先计划后执行)：对于长任务，在 Prompt 中要求 Agent 先生成一份完整的步骤清单（Plan），再逐一执行。这能有效防止 Agent 在中途“迷路”
3. **思维链 (Chain of Thought, CoT)**：在指令中加入“请一步步思考（Let's think step by step）”，能显著提高逻辑推理类任务的成功率

### 工具描述优化

1. **极其具体的参数描述**：不要只写 `city`，要写 `city: 城市的名称，例如 "Beijing" 或 "New York"`。
2. **使用场景指导**：在工具描述中加入“当用户询问天气或穿着建议时，请调用此工具”。
3. **少样本示例 (Few-shot)**：提供 1-2 个“问题 -> 思考 -> 调用工具 -> 结果”的例子。模型模仿例子的能力远强于理解枯燥的指令

### 动态上下文与反馈优化

1. **反思与自我修正 (Self-Reflection)**：在 Prompt 中加入一段逻辑：“在给出最终答案前，请检查你的回答是否完全解决了用户的问题，以及是否存在逻辑矛盾。”
2. **错误处理机制**：预设当工具返回空值或报错时的应对策略。
   - *提示词示例*：“如果搜索结果为空，请尝试更换关键词再次搜索，不要直接回复不知道。”
3. **动态少样本 (Dynamic Few-shot)**：根据用户的问题，从向量数据库中检索最相关的几个成功案例放入 Prompt 中（这需要配合 RAG 技术）。

### 核心原则二：给模型“思考”的时间

核心思想：如果任务太复杂，模型会像人一样因匆忙而犯错。你需要引导它进行逻辑推理。

1. 指定完成任务所需的步骤

   - 技巧：将复杂的任务拆解为具体的序列步骤。

   - 示例：
     - 第一步：用一句话总结以下文本。
       - 第二步：将总结翻译成英文。
       - 第三步：列出英文总结中的人名。
       - 第四步：输出一个 JSON 对象。

2. 指导模型在下结论前找出一个自己的解决方案

   - 技巧：不要直接问模型“这个答案对不对”，而是让它先自己算一遍，再对比。

   - 场景：比如让模型批改数学题，直接问对错它可能会被错误的解题步骤误导。

   - 示例：
     - 请先自己计算这道题的答案，然后将你的答案与学生的答案进行比较，判断学生的解答是否正确。

### 迭代与优化（写 Agent 的常态）

- 没有完美的 Prompt：写 Agent 并不是一次写对就万事大吉了。
- 流程化建议：
  - 初试：写一个简单清晰的 Prompt。
  - 分析：查看输出，发现哪里不满意（比如：太长了、格式不对、逻辑乱了）。
  - 改进：针对性地添加限制或示例。
  - 循环：重复上述过程直到稳定。

# RAG

## 什么叫RAG？

RAG = 检索增强生成（Retrieval-Augmented Generation）

## 作用是什么？

1. 解决大模型不知道新知识、幻觉的问题
2. 不用重新训练模型，成本低、安全可控

## 常见分类及对应的流程是什么？

### 基础 RAG

最简单：切分→向量→检索→生成。

适合简单问答。

### 高级 RAG（优化版）

1. 召回前：查询优化、重写
2. 召回中：多路召回、混合检索（关键词+向量）
3. 召回后：重排序（Rerank），上下文压缩

#### 召回前：

1. **多查询重写**
   1. **原理**：对原始查询，使用LLM生成N个语义相似但表述不同的查询变体
   2. **作用**：覆盖同一意图的不同表达方式，避免因措辞差异导致的漏检。
   3. **实现**：提示词设计为“请为以下问题生成5个语义相同但措辞不同的变体”。
   4. **后续处理**：并行检索所有变体，合并去重后送入LLM生成。
2. **子查询分解**
   - **原理**：将复杂、多跳的查询拆解为多个独立、简单的子查询。
   - **场景**：适用于需要对比、因果推理或多步骤推理的问题。例如，“比较A公司和B公司2023年的营收” → 拆解为“A公司2023年营收”和“B公司2023年营收”。
   - **实现**：通过思维链提示或预定义规则进行分解。可串行检索（依赖前一个检索结果进行下一步）或并行检索后合并。
3. **上下文嵌入**：
   - **原理**：将对话历史、用户画像或前序检索结果作为上下文，与当前查询拼接，形成完整的查询语句。
   - **场景**：多轮对话中消除指代（“它”、“那个方案”）和省略。

#### 召回中

| 概念         | 一句话解释                                                 |                                               |
| :----------- | :--------------------------------------------------------- | --------------------------------------------- |
| **多路召回** | 从**多个数据源或通路**分别检索，合并结果，提升召回覆盖面   |                                               |
| **混合检索** | 融合**向量+关键词**等多种检索技术，兼顾语义理解与精确匹配  | **向量检索**:理解语义、处理同义词、泛化能力强 |
|              |                                                            | **关键词检索**:精确匹配、可解释性强、速度快   |
| **关系**     | 混合检索是多路召回的**核心组成部分**，两者通常**配合使用** |                                               |

### 召回后

| 概念           | 一句话解释                               | 核心价值                            |
| :------------- | :--------------------------------------- | :---------------------------------- |
| **重排序**     | 用更精准的模型对初检结果**重新打分排序** | 提升排序精度，确保最相关文档进入LLM |
| **上下文压缩** | 对文档进行**提取/摘要/剪枝**，去除冗余   | 减少噪音、节省token、提升生成质量   |

### RAG + 知识库管理

带文档更新、去重、过滤、元数据过滤。

### 模块化 RAG

可插拔：不同场景用不同检索策略。

## 面试高频三连问（标准答案）

1. RAG 和 Fine-tuning 区别？
   1. RAG：外挂知识库，不改模型，安全、实时、成本低。
   2. 微调：改模型权重，适合固定风格/专业领域，成本高。

2. Agent 和普通 LLM 区别？
   1. LLM：你问啥它答啥，被动。
   2. Agent：有目标、会思考、会用工具、自主完成任务。

3. Agent 和工作流区别？
   1. 工作流：固定步骤，按流程跑。
   2. Agent：动态思考，自主决策下一步。

## 在RAG过程中，数据是如何获取和构造的（清洗去重过滤）

### 获取：

1. **非结构化数据**：PDF 手册、Word 文档、Markdown 笔记。
2. **半结构化数据**：HTML 网页、JSON 日志、邮件记录。
3. **结构化数据**：数据库表（SQL）、Excel 报表（通常需要转换为 Text-to-SQL 或特定的描述性文本）。

### 清洗

1. **格式剥离**：利用 `Unstructured` 或 `PyMuPDF` 解析文档，去除页眉、页脚、广告弹窗、非法字符（如 `\x0c`）。
2. **噪声过滤**：删除过短的句子（如“查看更多”、“点赞”）、乱码文本。
3. **语义增强**：对于图片、表格，利用多模态模型（如 GPT-4o-mini）生成**文本描述（Captioning）**，将其转化为可检索的文本。

### 切片

[详见切片详情]()

### 去重与过滤

1. **语义去重 (Semantic De-dup)**：

   - 计算所有 Chunk 的向量，通过 **Cosine Similarity** 识别相似度 > 0.95 的块。

   - **策略**：只保留最完整的一个，或者合并差异点。

2. **关键词过滤**：基于业务黑名单（如敏感词、过时版本号）过滤掉不应被检索的内容。

## RAG的文档切分

### 基于规则的切分

#### 一、固定长度切分

- **按字符数切分**：如512、1024字符，可设置重叠区域
- **按Token数切分**：以模型Token数为单位，更符合LLM处理边界
- **优点**：简单、可控、速度快
- **缺点**：可能切断语义完整性

#### 二、基于分隔符切分

- 按段落（`\n\n`）、句子（`.!?`）、章节标题切分
- 保留自然语义边界
- **优点**：语义完整性较好
- **缺点**：长度不固定，可能过长或过短

### 基于文档结构的切分

#### 三、Markdown/HTML结构切分

- 按标题层级（H1、H2、H3）切分
- 保留列表、表格、代码块完整性
- 适用于技术文档、网页内容

#### 四、PDF/Word文档结构切分

- 按页、章节、段落识别
- 结合布局分析（如[Unstructured.io](https://unstructured.io/)）
- 保留表格、图片等非文本元素

### 语义智能切分

#### 五、基于嵌入相似度切分

- 计算相邻句子的向量相似度
- 在相似度低的位置切分（语义转折点）
- 如LlamaIndex的`SemanticSplitterNodeParser`

#### 六、基于模型判别的切分

- 使用小模型预测切分点
- 如训练分类器判断句子是否为边界
- 更智能但成本较高

### 高级切分策略

#### 七、滑动窗口与重叠

- 相邻块设置重叠区域（10%-20%）
- 避免关键信息被截断在边界

#### 八、父子文档切分

- 大块（父）用于检索，小块（子）用于生成
- 结合粗粒度召回和细粒度上下文

#### 九、元数据关联切分

- 切分后保留来源信息（文件名、章节、页码）
- 支持后续过滤和溯源

#### 十、多粒度切分

- 同时生成多种粒度的块
- 检索时动态选择最合适的粒度

### 五、实践建议

| 场景          | 推荐方式            | 块大小                  |
| :------------ | :------------------ | :---------------------- |
| 通用问答      | 段落切分 + 语义切分 | 200-500 tokens          |
| 技术文档      | Markdown结构切分    | 500-1000 tokens         |
| 法律/学术论文 | 章节+段落切分       | 300-800 tokens          |
| 代码库        | 函数/类级别切分     | 按代码结构              |
| 长文本        | 父子文档策略        | 父:1000-2000,子:200-500 |

### 六、常用工具

- **LangChain**: `RecursiveCharacterTextSplitter`, `SemanticChunker`
- **LlamaIndex**: `SentenceSplitter`, `SemanticSplitterNodeParser`
- **[Unstructured.io](https://unstructured.io/)**: 文档结构解析
- **Chonkie**: 轻量级RAG切分库

选择切分方式时，需结合**文档类型、检索场景、模型限制**进行实验调优，通常需要A/B测试确定最优策略。

# Agent

## Agent 底层原理（面试官最爱深挖）

一句话：Agent = LLM 做大脑 + 工具调用 + 记忆 + 反思 + 规划

核心 5 组件（背这个）

1. 大脑（LLM）
   负责思考、决策、理解任务。

2. 记忆（Memory）
   1.  短期记忆：上下文
   2.  长期记忆：向量库/数据库

3. 工具（Tools）
   搜索、代码解释器、API、函数调用（FC）。

4. 规划（Planning）
   拆解任务、多步推理、自主决定怎么做。

5. 反思（Reflection）
   检查结果对不对，错了就修正。

## 标准执行流程（面试直接说）

1. 理解用户目标

2. 思考：我要做什么？需要哪些工具？

3. 调用工具获取信息

4. 继续推理，直到完成目标

5. 输出最终结果

## 多 Agent 是什么？

1. 多 Agent = 多个智能体分工协作完成复杂任务。

2. 特点

   1. 每个 Agent 有专属角色
   2. 互相通信、分工、协作
   3. 能处理复杂、多步骤、跨领域任务

3. 常见架构

   1. 集中式
      有一个“主管 Agent”分配任务。

   2. 分布式
      无中心，Agent 之间互相沟通。

   3. 分层式
      上层决策，下层执行。

4. 典型应用

   1.  代码开发团队（产品、前端、后端、测试）
   2.  内容创作团队
   3.  企业自动化流程

```python
from langchain_openai import ChatOpenAI
from langchain.agents import create_react_agent, AgentExecutor
from langchain.tools import tool
from langchain_core.prompts import PromptTemplate

# 1. 定义工具（使用装饰器）
@tool
def calculator(expression: str) -> float:
    """计算数学表达式。输入应为数学表达式，如 '2 + 3 * 4'"""
    return eval(expression)

@tool
def get_weather(city: str) -> str:
    """获取指定城市的天气。输入城市名称，如 '北京'"""
    weather_data = {
        "北京": "晴天，25°C，风力2级",
        "上海": "多云，22°C，风力3级",
        "深圳": "雨天，28°C，风力1级"
    }
    return weather_data.get(city, f"未找到{city}的天气信息")

# 2. 初始化LLM
llm = ChatOpenAI(
    model="gpt-4",  # 或 "gpt-3.5-turbo"
    temperature=0,
    api_key="your-api-key"  # 或设置环境变量 OPENAI_API_KEY
)

# 3. 创建工具列表
tools = [calculator, get_weather]

# 4. 创建Agent（使用ReAct模板）
from langchain import hub
prompt = hub.pull("hwchase17/react")  # 从LangChain Hub拉取标准ReAct模板

agent = create_react_agent(
    llm=llm,
    tools=tools,
    prompt=prompt
)

# 5. 创建Agent执行器
agent_executor = AgentExecutor(
    agent=agent,
    tools=tools,
    verbose=True,  # 打印思考过程
    max_iterations=5,
    handle_parsing_errors=True  # 处理解析错误
)

# 6. 运行
response = agent_executor.invoke({
    "input": "北京今天天气怎么样？然后帮我算一下 25 * 4 + 10"
})
print(response["output"])
```

## 为什么要做agent

之所以要做 Agent 项目，而不是停留在简单的 ChatBot 或 RAG 阶段，主要基于以下三个维度的技术必然性和商业价值：

1. 从“生成内容”到“解决问题”的跨越
   1. 传统 LLM 主要是**文本生成器**，它能告诉你“怎么做”，但不能“替你做”。
   2. **Agent 的价值**：Agent 具备**工具使用（Tool Use）**能力。它能直接调用 API、操作数据库或执行脚本。
2. 处理复杂长路径任务：
   1. 当一个任务需要多个步骤、多次决策且中间结果会影响后续选择时，单次 Prompt 无法胜任
   2. **Agent 的价值**：通过**规划（Planning）\**和\**递归式思考（ReAct）**，Agent 可以将大目标拆解为小步骤。
3. 连接私有数据与异构系统
   1. 企业内部的数据往往分散在 ERP、CRM、代码库或本地文档中
   2. **Agent 的价值**：Agent 可以作为**中间层**，理解自然语言意图后，实时查询异构系统并进行数据加工。

## 平时用 AI 工具做什么？选一个最常用的举个例子？

**工业调度**：Agent 可以实时监控 AGV（自动导引运输车）的状态，当发现异常时，自主调用接口重新规划路径，而不是等待人工干预

之所以使用agent，而不是用定时器去拉取：

1. 你只需要把这些接口封装成 Agent 的 **Tools**。Agent 会根据当前任务（Goal），自主决定调用顺序：先去 ERP 看哪个单子急，再去 WMS 看哪个库位近，最后才去调用路径规划。
2. 更新更灵活：以通过更新 **System Prompt** 或增加一个新 **Tool** 来扩展能力。它对复杂逻辑的解耦效果更好，更适合需求多变的生产环境
   1. 如果优先级的判定条件、字段变了，我只需要改Prompt即可，而不需要更新代码和字段


# 微调

## SFT阶段有哪些bad case又是怎么解决的？

在 **SFT（Supervised Fine-Tuning，监督微调）** 阶段，模型的效果高度依赖于指令对（Instruction-Output Pairs）的质量。大家也都知道“垃圾进，垃圾出”（Garbage In, Garbage Out）是 SFT 最大的挑战

###  模型幻觉与知识冲突 (Hallucination)

- **现象**：模型对于不知道的问题开始“一本正经地胡说八道”，或者 SFT 数据里的知识与模型预训练阶段的知识发生冲突。
- **解决方法**：
  - **知识对齐**：对 SFT 数据进行事实核查（可以使用强模型如 GPT-4 进行辅助验证）。
  - **引入“拒绝回答”范式**：在数据集中加入一定比例的“我不知道”、“根据现有信息无法回答”的案例，训练模型的边界感。
  - **RAG 结合**：对于时效性强的知识，不强求 SFT 记忆，而是训练模型生成“查询工具”的指令。

### 回复格式坍塌

- **现象**：要求模型输出 JSON 或 Markdown 表格，但模型输出的括号不闭合、字段缺失或包含多余解释
- **原因**：SFT 数据中格式不规范，或者格式样本多样性不足，导致模型没能学死“结构化输出”的约束。
- **解决方法**：
  - **Schema 约束强化**：在 Input 侧加入严格的 JSON Schema 定义。
  - **损失函数加权**：对格式关键 Token（如 `{`, `[`, `]`）增加 Loss 权重。
  - **Few-shot 注入**：在 SFT 的 Prompt 示例中，始终保持统一且严谨的格式规范

### 灾难性遗忘 (Catastrophic Forgetting)

- **现象**：模型学会了特定的业务逻辑（如 MES 调度），但失去了通用的对话能力或逻辑推理能力。
- **原因**：SFT 数据过于单一（全是一个领域的任务），导致模型权重偏移过大。
- **解决方法**：
  - **通用数据混入 (Data Mixing)**：在业务 SFT 数据中掺入 5%~10% 的通用高质量对话数据（如 Alpaca 或 ShareGPT 数据集）。
  - **LoRA 微调**：使用参数高效微调（PEFT）技术，仅更新少量旁路参数，保持基座模型大部分权重冻结。

### 训练数据中的“复读机”与模式过拟合 (Pattern Overfitting)

- **现象**：模型每一句话都以相同的口吻开头（如“好的，关于您的问题...”），或者回复极短、无营养。
- **原因**：数据集中存在大量重复的句式模板。
- **解决方法**：
  - **多样性清洗**：利用语义向量对 SFT 数据进行聚类，剔除在同一个聚类中心下过于密集的重复模式数据。
  - **长度奖励与惩罚**：在构造数据时，确保 Output 的长度分布合理，避免全是短句
